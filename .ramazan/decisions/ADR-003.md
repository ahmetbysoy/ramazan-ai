# ADR-003

## Decision
Establish TaskStore (TaskEngine) as the Absolute Single Source of Truth for State Computation via `StateManager.recompute()`.

## Context
In previous iterations, `.ramazan/state.json` diverged from `.ramazan/tasks/*.json`:
1. `totalTasks` and `completedTasks` were manually mutated in CLI scripts and web UI endpoints rather than derived deterministically.
2. During the rapid creation of the mobile monkey game, `TASK-004.json` was not committed to disk before `TASK-005` was created, leaving an ID gap and state mismatch (`completedTasks` had 4 entries while `TASK-004` was missing).
3. `status` showed `IN_PROGRESS` despite 100% completion.

## Alternatives
- Continue maintaining separate state caches with manual sync hooks.
- Fully eliminate `state.json` and compute everything purely in memory on every command.
- Retain `state.json` as a fast-read cache, but make all write operations strictly deterministic via `StateManager.recompute()` derived directly from `TaskEngine` (Chosen).

## Reason
1. Sections 46 & 49 of the specification mandate deterministic, reproducible state.
2. Deriving `totalTasks`, `completedTasks`, `failedTasks`, `blockedTasks`, and `progress` directly from `TaskEngine.tasks` eliminates all risk of split-brain state drift.
3. Idempotent recomputation ensures that repeated state loads or audits produce identical output.

## Consequences
- No component is permitted to manually assign `state.totalTasks` or `state.progress`.
- All task state transitions must be saved to their individual `.ramazan/tasks/TASK-XXX.json` files first, followed by a deterministic state recomputation.
